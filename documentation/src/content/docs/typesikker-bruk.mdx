Klasser og dataattributter gjør komponentene rammeverksuavhengige, men alt er strenger:

```html
<button class="fs-button" data-variant="secundary">Lagre utkast</button>
```

Knappen får primærstilen. Ingen feilmelding — bare en variant som stille aldri ble brukt. Derfor finnes `fs`.

## Én inngang

```ts
import { fs } from "@fristil/designsystem"

<button {...fs.button({ variant: "secondary" })}>Lagre utkast</button>
<input {...fs.input({ type: "email", state: "invalid" })} />
<span {...fs.badge({ color: "success" })}>Innvilget</span>
<a {...fs.link()} href="/kvittering">Se kvittering</a>
```

Skriv `fs.` i editoren, så ser du hele systemet. Hver komponent er en funksjon som tar et valgobjekt og returnerer attributtene du sprer inn i elementet — samme form for alle.

Returverdiene er vanlige objekter. Derfor virker samme API i React, Astro, Datastar og ren HTML.

:::note[Bruker du React?]
Importer fra `@fristil/designsystem/react` i stedet. Kallstedene er identiske, men returverdien bruker `className` og `htmlFor`.

`fs` returnerer `class` og `for`, slik attributtene faktisk heter i HTML. React godtar dem — de havner riktig i DOM-en — men utviklingsbygget skriver «Invalid DOM property `class`. Did you mean `className`?» i konsollen for hvert element. Med et helt felt blir det to advarsler per felt.

Ren HTML, Astro og Datastar tar `class` og `for` som de er, og bruker hovedinngangen.
:::

## Standardverdier gir ingen attributter

```ts
fs.button()
// { class: "fs-button" }

fs.button({ variant: "primary" })
// { class: "fs-button" } — primær er standard i CSS-en

fs.button({ variant: "danger" })
// { class: "fs-button", "data-variant": "danger" }
```

Du sier alltid hvilken variant du vil ha; funksjonen vet når attributtet kan utelates.

## Lovlige verdier og vakter ligger på komponenten

```ts
fs.button.variants
// readonly ["primary", "secondary", "ghost", "danger"]

fs.button.isVariant("ghost")  // true
fs.button.isVariant("gost")   // false
```

Samme mønster overalt: `fs.badge.colors` og `fs.badge.isColor`, `fs.input.types` og `fs.input.isType`.

Kommer verdien fra et API, en URL eller `localStorage`, er den en `string` TypeScript ikke kan garantere noe om. Vakten gir en gyldig verdi eller en trygg reserve:

```ts
const svar = await hentKnappeoppsett()
const variant = fs.button.isVariant(svar.variant) ? svar.variant : "primary"

fs.button({ variant })
```

Etter vakten vet TypeScript at verdien er en `ButtonVariant`.

## `fs.input` kan ikke komme i utakt

Skrevet for hånd må `type` og `data-variant` stemme overens, ellers skjer ingenting når brukeren trykker på ikonet.

```ts
fs.input({ type: "date" })
// { class: "fs-input", type: "date", "data-variant": "date" }

fs.input({ type: "email" })
// { class: "fs-input", type: "email" } — e-post har ikke noe ikon
```

Én verdi styrer begge. Det samme gjelder tilstand: `state: "invalid"` gir både `data-state` og `aria-invalid`.

## Ett begrep, én betydning

| Valg | Hva det betyr | Hvor |
| --- | --- | --- |
| `variant` | Visuell vekt eller betydning | `button`, `helpText`, `errorText` |
| `color` | Hva en status betyr | `badge` |
| `state` | Valideringstilstand | `input`, `textarea`, `select` |
| `type` | HTML-typen på feltet | `input` |

`state` er én type på tvers av de tre feltkomponentene, så en verdi kan sendes mellom dem uten konvertering:

```ts
const tilstand = fs.isState(fraServer) ? fraServer : "default"

fs.input({ state: tilstand })
fs.textarea({ state: tilstand })
fs.select({ state: tilstand })
```

## `fs.field` kobler et helt felt

Fem koblinger må stemme samtidig. `fs.field` regner dem ut:

```ts
const felt = fs.field({
	id: "epost",
	required: "symbol",
	help: true,
	error: true,
	invalid: !erGyldig,
})

<label {...felt.label}>E-postadresse</label>
<input {...fs.input({ type: "email" })} {...felt.control} />
<p {...fs.helpText()} {...felt.help}>Vi sender kvittering hit.</p>
<p {...fs.errorText()} {...felt.error}>Skriv en gyldig adresse.</p>
```

Du får `for`, `id`, `aria-describedby`, `aria-invalid` og `data-state` ferdig utregnet.

Legg merke til at `fs.input` bare får `type`. Tilstanden ligger i `felt.control`, og de to overlapper med vilje ikke — sendte du `state` til begge, ville `aria-invalid` blitt skrevet ut to ganger i maler som gjengir attributtene bokstavelig, som Astro og ren HTML. `felt.state` finnes fortsatt hvis du vil drive noe annet med den.

Feilmeldingen tas med i `aria-describedby` **bare når feltet er ugyldig** — ellers ville skjermleseren pekt på et skjult element. `felt.error` inneholder `hidden` når den ikke skal vises.

:::note[Samme kjerne som `<fs-field>`]
[Field](../components/field/) gjør samme utregning, men på elementer som allerede står i DOM-en. De deler kode, så kontrakten finnes ett sted.

Velg `<fs-field>` for vanlig HTML, `fs.field` når du bygger markupen selv.
:::

## I praksis: en gjenbrukbar knapp i React

```tsx
import { fs } from "@fristil/designsystem/react"
import type { ButtonVariant } from "@fristil/designsystem"
import type { ComponentProps } from "react"

type Props = ComponentProps<"button"> & {
	variant?: ButtonVariant
}

export function Knapp({ variant, ...rest }: Props) {
	return <button {...fs.button({ variant })} {...rest} />
}
```

Bytter teamet rammeverk, er det disse tolv linjene som skrives om — ikke designsystemet.

`ComponentProps<"button">` tar med `ref`, som siden React 19 er en vanlig prop og følger med gjennom `{...rest}` uten `forwardRef`. `ComponentPropsWithRef` og `ComponentPropsWithoutRef` trengs ikke lenger.

## Web-komponentene

TypeScript kjenner ikke `<fs-field>`, `<fs-calendar>` og `<fs-date-field>` uten videre. Importer typene én gang i en `.d.ts`-fil:

```ts
// src/fristil.d.ts
import "@fristil/designsystem/react-jsx"
```

Da får attributtene autofullføring og sjekk:

```tsx
<fs-field required-marker="text" />      // ok
<fs-field required-marker="tekst" />     // feil: "none" | "symbol" | "text"
<fs-date-field labell="Reisedato" />     // feil: ukjent attributt
<fs-date-field helpText="DD-MM-ÅÅÅÅ" />  // feil: attributtet heter help-text
```

Ren HTML, Astro og Datastar trenger ikke dette — der er `<fs-field>` bare en HTML-tagg.

## Det typene ikke fanger

**Attributtene kan spres på feil element.** `<div {...fs.button({ variant: "danger" })} />` kompilerer — returverdien er bare et objekt med HTML-attributter.

**Returtypen på `type` er bredere enn verdien du sendte inn.** `fs.input({ type: "date" }).type` er hele unionen, ikke `"date"`.

## Når du kan hoppe over det

`fs` er valgfritt. Uten TypeScript eller byggesteg er dette like gyldig:

```html
<button class="fs-button" data-variant="secondary">Lagre utkast</button>
```

Resultatet er identisk. Forskjellen er hvor tidlig du får vite at du skrev `secundary`.

Vil du bare ha én komponent:

```ts
import { button } from "@fristil/designsystem/button"
```

Subpath-ene returnerer `class` og `for`, som hovedinngangen. React-varianten finnes bare som samlet `fs`.
