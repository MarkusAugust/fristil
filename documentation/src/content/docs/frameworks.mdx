CSS-komponentene er klasser og krever ingenting av rammeverket. Web-komponentene trenger av og til oppsett, og denne siden samler det.

Alle web-komponentene registreres på samme måte, og hver av dem har sin egen side med eksempler per miljø: [Field](../components/field/), [Tabs](../components/tabs/), [Dialog](../components/dialog/), [Error Summary](../components/error-summary/), [Popover](../components/popover/), [Suggestion](../components/suggestion/), [Toast](../components/toast/), [Session Timeout](../components/session-timeout/) og [Connection Status](../components/connection-status/).

Tre ting gjelder overalt:

1. **`define`-funksjonen må kjøre én gang** når appen starter, før elementet brukes.
2. **Boolske attributter er sanne så lenge de finnes.** `invalid="false"` gjør feltet ugyldig. Skal attributtet bort, må det fjernes helt.
3. **Serveren skriver markupen, komponenten fester oppførsel.** Se [Markup og oppførsel](../markup-and-behaviour/) for hvorfor, og hva det betyr i hvert av miljøene.

React har i tillegg `@lo-tek/interfaces/react`, som gir `className` og `htmlFor`. Uten den skriver React «Invalid DOM property» i konsollen for hvert element. De andre bruker HTML-navnene direkte.

## Plain HTML

Ingen byggverktøy, ingen pakkebehandler i nettleseren.

```html
<!doctype html>
<html lang="nb">
  <head>
    <meta charset="utf-8" />
    <link rel="stylesheet" href="/node_modules/@lo-tek/interfaces/src/tokens/tokens.css" />
    <link rel="stylesheet" href="/node_modules/@lo-tek/interfaces/src/components/frame/field/field.css" />
    <link rel="stylesheet" href="/node_modules/@lo-tek/interfaces/src/components/css/button/button.css" />
    <!-- Eller alt i én fil: /node_modules/@lo-tek/interfaces/dist/lotek.css -->
  </head>
  <body>
    <form id="skjema">
      <lt-field>
        <label class="lt-label" for="navn" data-required="symbol">Fullt navn</label>
        <input class="lt-input" id="navn" type="text" name="navn" required />
        <p class="lt-error-text" hidden>Fyll inn navnet ditt.</p>
      </lt-field>

      <button class="lt-button" type="submit">Send</button>
    </form>

    <script type="module">
      import { defineLtField } from "/node_modules/@lo-tek/interfaces/dist/components/frame/field/lt-field.js"
      defineLtField()

      document.getElementById("skjema").addEventListener("submit", (hendelse) => {
        hendelse.preventDefault()
        console.log(Object.fromEntries(new FormData(hendelse.currentTarget)))
      })
    </script>
  </body>
</html>
```

`new FormData(...)` plukker opp feltet av seg selv, fordi `<lt-field>` holder elementene i vanlig DOM.

CSS-komponentene krever ikke engang skriptet:

```html
<link rel="stylesheet" href="/node_modules/@lo-tek/interfaces/src/tokens/tokens.css" />
<link rel="stylesheet" href="/node_modules/@lo-tek/interfaces/src/components/css/button/button.css" />
<!-- Eller alt i én fil: /node_modules/@lo-tek/interfaces/dist/lotek.css -->

<button class="lt-button" data-variant="secondary">Lagre utkast</button>
```

Dette er delen som overlever lengst. Klassen og dataattributtet er en kontrakt nettleseren forstår direkte.

:::caution[TypeScript hører ikke hjemme i `<script type="module">`]
En `<script>`-tagg i en HTML-fil kjøres av nettleseren som vanlig JavaScript. Skriver du `hendelse as CustomEvent<…>` der, får du `SyntaxError` og hele skriptet stopper. Type-syntaks krever et byggesteg.
:::

## React

<Tabs>
  <TabItem label="Oppsett">
    ```tsx
    // main.tsx
    import "@lo-tek/interfaces/tokens.css"
    import "@lo-tek/interfaces/field.css"
    import "@lo-tek/interfaces/suggestion.css"

    import { defineLt } from "@lo-tek/interfaces/register"

    defineLt()
    ```

    Kallet står øverst i modulen, ikke i en `useEffect`. En effekt kjører etter første tegning, så elementene i markupen er vanlige `HTMLElement` i det React tegner dem, og et kall på `show()` eller `reportFailure()` før effekten feiler med «is not a function». Funksjonen gjør ingenting på en server, så den kan stå i en rotmodul som kjøres begge steder, som i TanStack Start. Bruker du én komponent, kall dens egen funksjon, som `defineLtTabs()`, og hold resten utenfor det som bygges.

    Bruker du CSS-komponentene, importer `lt` fra React-inngangen:

    ```tsx
    import { lt } from "@lo-tek/interfaces/react"

    <button {...lt.button({ variant: "secondary" })}>Lagre utkast</button>
    ```

    Står dette i `main.tsx` før `createRoot`, er elementene registrert før React rekker å tegne noe.
  </TabItem>
  <TabItem label="TypeScript-typer">
    Importer typene for web components én gang. Legg importen i en `.d.ts`-fil, så havner den aldri i bygget:

    ```ts
    // src/lotek.d.ts
    import "@lo-tek/interfaces/react-jsx"
    ```

    Uten den kjenner ikke TypeScript `<lt-field>` i det hele tatt:

    ```
    Property 'lt-field' does not exist on type 'JSX.IntrinsicElements'
    ```

    Med den får du autofullføring og feilmelding på attributtene:

    ```tsx
    <lt-field describedBy="vilkar" />       // feil: attributtet heter described-by
    <lt-toast closeLabel="Lukk" />           // feil: attributtet heter close-label
    <lt-connection-status offline="Nede" />  // feil: ukjent attributt
    ```

    :::caution[Bare én kopi av `@types/react`]
    Typene virker ved at pakken utvider Reacts `JSX.IntrinsicElements`. Har prosjektet to installasjoner av `@types/react`, noe som lett skjer i et monorepo, utvider pakken den ene mens koden din bruker den andre, og elementene forblir ukjente. Kjør `npm ls @types/react` hvis noe ser rart ut.
    :::
  </TabItem>
  <TabItem label="Bruk">
    Et felt skriver du med `lt.field()`. Koblingen mellom ledeteksten, feltet og feilmeldingen står da i markupen React selv rendrer, og ingenting må registreres.

    ```tsx
    // Kontaktskjema.tsx
    import { lt } from "@lo-tek/interfaces/react"
    import { useId, useState } from "react"

    export function Kontaktskjema() {
      const [navn, setNavn] = useState("")
      const [berørt, setBerørt] = useState(false)

      const ugyldig = berørt && navn.trim() === ""
      const felt = lt.field({
        id: useId(),
        required: "symbol",
        error: true,
        invalid: ugyldig,
      })

      return (
        <form onSubmit={(e) => e.preventDefault()}>
          <label {...felt.label}>Fullt navn</label>
          <input
            {...lt.input({ type: "text" })}
            {...felt.control}
            name="navn"
            required
            value={navn}
            onChange={(e) => setNavn(e.target.value)}
            onBlur={() => setBerørt(true)}
          />
          <p {...lt.errorText()} {...felt.error}>Fyll inn navnet ditt.</p>

          <button {...lt.button()} type="submit">Send</button>
        </form>
      )
    }
    ```

    Id-en kommer fra `useId()`, så serveren og nettleseren lager den samme.

    :::caution[Bruk ikke web componenten for felt i React med server-rendring]
    Komponenten skriver koblingen på elementene før React hydrerer, og React melder avvik på ledeteksten, feltet og feilmeldingen. Se [Field](../components/field/) for når `<lt-field>` er riktig vei.
    :::

    De andre web-komponentene bruker du sammen med byggefunksjonen, som `lt.tabs()` i `<lt-tabs>`. Boolske attributter på dem skrives `open={åpen || undefined}`, aldri `open=""` eller `open={åpen}`: React 18 skriver `false` som attributtet `open="false"`, som er sant. React 19 setter egenskapen til `""`, og komponenten leser den som usann.
  </TabItem>
</Tabs>

## Astro

En `.astro`-fil er HTML med frontmatter over. Stilarkene importeres der, og `lt` brukes rett i malen, siden Astro støtter spredning som JSX.

```astro
---
import { lt } from "@lo-tek/interfaces"
import "@lo-tek/interfaces/tokens.css"
import "@lo-tek/interfaces/button.css"
import "@lo-tek/interfaces/badge.css"
---

<button {...lt.button({ variant: "secondary" })}>Lagre utkast</button>
<span {...lt.badge({ color: "success" })}>Innvilget</span>
```

Kjøres ved bygging. Ut kommer ren HTML:

```html
<button class="lt-button" data-variant="secondary">Lagre utkast</button>
<span class="lt-badge" data-color="success">Innvilget</span>
```

Null JavaScript sendt til nettleseren. `lt` er borte når siden er bygget.

### Felt uten JavaScript

`lt.field()` regner ut koblingen i frontmatteret, så den også blir statisk HTML:

```astro
---
import { lt } from "@lo-tek/interfaces"
import "@lo-tek/interfaces/tokens.css"
import "@lo-tek/interfaces/field.css"

const epost = lt.field({ id: "epost", required: "symbol", help: true, error: true })
---

<label {...epost.label}>E-postadresse</label>
<input {...lt.input({ type: "email" })} {...epost.control} name="epost" required />
<p {...lt.helpText()} {...epost.help}>Vi sender kvittering hit.</p>
<p {...lt.errorText()} {...epost.error}>Skriv en gyldig adresse.</p>
```

Ingen `<lt-field>`, ingen kjøretid.

### Web-komponenter i Astro

Skal feltet kunne bli ugyldig mens brukeren står i det, må komponenten registreres. Astro pakker `<script>`-tagger og kjører dem på klienten:

```astro
---
import "@lo-tek/interfaces/tokens.css"
import "@lo-tek/interfaces/field.css"
---

<lt-field>
  <label class="lt-label" for="navn" data-required="symbol">Fullt navn</label>
  <input class="lt-input" id="navn" type="text" name="navn" required />
  <p class="lt-error-text" hidden>Fyll inn navnet ditt.</p>
</lt-field>

<script>
  import { defineLtField } from "@lo-tek/interfaces/field"
  defineLtField()
</script>
```

`customElements` finnes bare i nettleseren, så registreringen kan ikke stå i frontmatteret. Et `<script>` i malen er alt som skal til: komponentene er vanlige web components, og trenger verken en Astro-integrasjon eller et `client:`-direktiv.

### Astro og Datastar

Astro bygger HTML-en, Datastar gir den oppførsel, og ingen av delene krever en komponentmodell i nettleseren.

## HTML med Datastar

[Datastar](https://data-star.dev) legger reaktivitet på vanlig HTML med `data-*`-attributter. Ett skript, ingen byggesteg. Samme premiss som LO-TEK.

```html
<script
  type="module"
  src="https://cdn.jsdelivr.net/gh/starfederation/datastar@v1.0.4/bundles/datastar.js"
></script>
```

Stilarkene lenkes, siden en nettleser ikke slår opp et pakkenavn:

```html
<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/@lo-tek/interfaces@VERSJON/src/tokens/tokens.css">
<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/@lo-tek/interfaces@VERSJON/src/components/frame/field/field.css">
<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/@lo-tek/interfaces@VERSJON/src/components/css/button/button.css">
<!-- Eller alt i én fil: https://cdn.jsdelivr.net/npm/@lo-tek/interfaces@VERSJON/dist/lotek.css -->
```

```html
<form
  data-signals="{navn: '', beroert: false}"
  data-computed:ugyldig="$beroert && $navn.trim() === ''"
>
  <lt-field>
    <label class="lt-label" for="navn" data-required="symbol">Fullt navn</label>
    <input
      class="lt-input"
      id="navn"
      type="text"
      name="navn"
      data-bind:navn
      data-on:blur="$beroert = true"
    />
    <p class="lt-error-text" hidden data-attr:hidden="!$ugyldig">Fyll inn navnet ditt.</p>
  </lt-field>

  <button class="lt-button" type="submit">Send</button>
</form>

<script type="module">
  import { defineLtField } from
    "https://cdn.jsdelivr.net/npm/@lo-tek/interfaces@VERSJON/dist/components/frame/field/lt-field.js"

  defineLtField()
</script>
```

Tre attributter gjør hele jobben:

- `data-signals` oppretter tilstanden.
- `data-computed:ugyldig` utleder valideringen av den.
- `data-bind:navn` binder feltet begge veier, og `data-on:blur` markerer at brukeren har forlatt det.

`data-attr:hidden` på feilmeldingen knytter Datastar til komponenten: den **skjuler feilmeldingen når feltet er gyldig og viser den når det er ugyldig**, og `<lt-field>` regner feltet som ugyldig når feilmeldingen synes.

`lt` brukes eventuelt på serveren eller i byggesteget. Datastar trenger den ikke i nettleseren.

### HTML fra serveren

Datastar kan la serveren sende HTML underveis, over Server-Sent Events. Se [`@starfederation/datastar-sdk`](https://github.com/starfederation/datastar-typescript).

En web component oppgraderer seg selv når den settes inn i dokumentet, så lenge `defineLtField()` har kjørt én gang. Serveren kan derfor sende dette som ren HTML:

```html
<lt-field>
  <label class="lt-label" for="epost" data-required="text">E-postadresse</label>
  <input class="lt-input" id="epost" type="email" value="ola@" />
  <p class="lt-help-text">Vi sender kvittering hit.</p>
  <p class="lt-error-text">Skriv en gyldig adresse.</p>
</lt-field>
```

Komponenten setter da `lt-label`, gir hjelpeteksten og feilmeldingen id, legger på `aria-invalid` fordi feilmeldingen synes, og bygger `aria-describedby`, uten at det sendes JavaScript med for akkurat dette feltet. Feltet har ingen id komponenten har laget, så neste oppdatering fra serveren kjenner det igjen.

Det er poenget med at `ramme`-komponentene bor i vanlig DOM: markupen er dataen, og tilgjengeligheten kobles der den lander.

## Kjente fallgruver

| Symptom | Årsak |
| --- | --- |
| En `<lt-toast>` eller `<lt-connection-status>` viser ingenting, eller et `<lt-session-timeout>` varsler aldri | `define`-funksjonen har ikke kjørt. `<lt-toast>` og `<lt-connection-status>` lager innholdet sitt selv, så uten registrering er elementet tomt, og `<lt-session-timeout>` teller ikke tiden. En `ramme`-komponents markup er din og står der uansett, bortsett fra at Tabs bare viser det første panelet og Suggestion skjuler lista til de er registrert |
| Feilmeldingen vises aldri, og feltet regnes som gyldig | `hidden="false"` er satt på feilmeldingen, og det skjuler den like fullt. Attributtet må fjernes, ikke settes til `false` |
| `SyntaxError` i nettleseren | TypeScript-syntaks i en `<script type="module">` uten byggesteg |
| Stilene mangler | `tokens.css` er ikke importert |
| React: «Invalid DOM property `class`» | Importer `lt` fra `@lo-tek/interfaces/react` |
