Komponentene styres med klasser og dataattributter. Det gjør dem uavhengige av rammeverk, men det betyr også at alt er strenger:

```html
<button class="fs-button" data-variant="secundary">Lagre utkast</button>
```

Knappen over får primærstilen. Ingen feilmelding, ingen advarsel — bare en variant som stille aldri ble brukt.

Derfor finnes `fs`.

## Én inngang

```ts
import { fs } from "@fristil/designsystem"

<button {...fs.button({ variant: "secondary" })}>Lagre utkast</button>
<input {...fs.input({ type: "email", state: "invalid" })} />
<span {...fs.badge({ color: "success" })}>Innvilget</span>
<a {...fs.link()} href="/kvittering">Se kvittering</a>
```

Skriv `fs.` i editoren, så ser du hele systemet. Hver komponent er en funksjon som tar et valgobjekt og returnerer attributtene du sprer inn i elementet. Formen er den samme for alle, så du lærer den én gang.

Returverdiene er vanlige objekter. Det er grunnen til at det samme API-et virker i React, Astro og ren HTML — alle kan spre et objekt inn i et element.

:::note[Bruker du React?]
Importer fra `@fristil/designsystem/react` i stedet. Kallstedene er identiske, men returverdien bruker `className` og `htmlFor`.

`fs` returnerer `class` og `for`, slik attributtene faktisk heter i HTML. React godtar dem — de havner riktig i DOM-en — men utviklingsbygget skriver «Invalid DOM property `class`. Did you mean `className`?» i konsollen for hvert element. Med et helt felt blir det to advarsler per felt.

Ren HTML, Astro og Datastar tar `class` og `for` som de er, og bruker hovedinngangen.
:::

## Standardverdier gir ingen attributter

```ts
fs.button()
// { class: "fs-button" }

fs.button({ variant: "primary" })
// { class: "fs-button" } — primær er standard i CSS-en

fs.button({ variant: "danger" })
// { class: "fs-button", "data-variant": "danger" }
```

Du sier alltid hvilken variant du vil ha, og funksjonen vet når attributtet kan utelates. Det er én ting mindre å holde styr på.

## Lovlige verdier og vakter ligger på komponenten

```ts
fs.button.variants
// readonly ["primary", "secondary", "ghost", "danger"]

fs.button.isVariant("ghost")  // true
fs.button.isVariant("gost")   // false
```

Skriv `fs.button.` og editoren viser både variantene og vakten. Samme mønster overalt: `fs.badge.colors` og `fs.badge.isColor`, `fs.input.types` og `fs.input.isType`.

Kommer verdien fra et API, en URL-parameter eller `localStorage`, er den en `string` TypeScript ikke kan garantere noe om. Vakten gjør den om til en gyldig verdi eller en trygg reserve:

```ts
const svar = await hentKnappeoppsett()
const variant = fs.button.isVariant(svar.variant) ? svar.variant : "primary"

fs.button({ variant })
```

Etter `isVariant(...)` vet TypeScript at verdien er en `ButtonVariant`, ikke bare en `string`.

## `fs.input` kan ikke komme i utakt

Skriver du et datofelt for hånd, må `type` og `data-variant` stemme overens — ellers får du et felt som ser ut som et datofelt, men der ingenting skjer når brukeren trykker på ikonet.

```ts
fs.input({ type: "date" })
// { class: "fs-input", type: "date", "data-variant": "date" }

fs.input({ type: "email" })
// { class: "fs-input", type: "email" } — e-post har ikke noe ikon
```

Én verdi styrer begge. Feilen er ikke lenger mulig å gjøre.

Det samme gjelder tilstand: `state: "invalid"` gir både `data-state` for fargen og `aria-invalid` for skjermleseren. To ting som alltid må følges ad, satt ett sted.

## Ett begrep, én betydning

| Valg | Hva det betyr | Hvor |
| --- | --- | --- |
| `variant` | Visuell vekt eller betydning | `button`, `helpText`, `errorText` |
| `color` | Hva en status betyr | `badge` |
| `state` | Valideringstilstand | `input`, `textarea`, `select` |
| `type` | HTML-typen på feltet | `input` |

`state` er én type på tvers av de tre feltkomponentene, så en verdi kan sendes mellom dem uten konvertering:

```ts
const tilstand = fs.isState(fraServer) ? fraServer : "default"

fs.input({ state: tilstand })
fs.textarea({ state: tilstand })
fs.select({ state: tilstand })
```

## `fs.field` kobler et helt felt

Et felt med ledetekst, hjelpetekst og feilmelding krever fem koblinger som alle må stemme samtidig. `fs.field` regner dem ut for deg:

```ts
const felt = fs.field({
	id: "epost",
	required: "symbol",
	help: true,
	error: true,
	invalid: !erGyldig,
})

<label {...felt.label}>E-postadresse</label>
<input {...fs.input({ type: "email", state: felt.state })} {...felt.control} />
<p {...fs.helpText()} {...felt.help}>Vi sender kvittering hit.</p>
<p {...fs.errorText()} {...felt.error}>Skriv en gyldig adresse.</p>
```

Du får `for`, `id`, `aria-describedby` og `aria-invalid` ferdig utregnet, og `felt.state` sendes rett inn i `fs.input`.

Legg merke til én detalj: feilmeldingen tas med i `aria-describedby` **bare når feltet faktisk er ugyldig**. Ellers ville skjermleseren pekt på et skjult element. `felt.error` inneholder `hidden` når den ikke skal vises.

:::note[Samme kjerne som `<fs-field>`]
[Field](../components/field/) gjør nøyaktig den samme utregningen, men på elementer som allerede står i DOM-en. De deler kode, så kontrakten finnes ett sted i systemet og kan ikke gå fra hverandre.

Velg `<fs-field>` når du vil skrive vanlig HTML og la komponenten koble den. Velg `fs.field` når du bygger markupen i et rammeverk og heller vil ha koblingen som data.
:::

## I praksis: en gjenbrukbar knapp i React

```tsx
import { fs } from "@fristil/designsystem/react"
import type { ButtonVariant } from "@fristil/designsystem"
import type { ComponentProps } from "react"

type Props = ComponentProps<"button"> & {
	variant?: ButtonVariant
}

export function Knapp({ variant, ...rest }: Props) {
	return <button {...fs.button({ variant })} {...rest} />
}
```

Tolv linjer. Bytter teamet rammeverk, er det disse tolv linjene som skrives om — ikke designsystemet.

`ComponentProps<"button">` tar med `ref`, og siden React 19 er `ref` en vanlig prop. Den følger derfor med gjennom `{...rest}` uten `forwardRef`. (De eldre variantene `ComponentPropsWithRef` og `ComponentPropsWithoutRef` trengs ikke lenger.)

## Web-komponentene

`fs` dekker CSS-komponentene. De egendefinerte elementene — `<fs-field>`, `<fs-calendar>` og `<fs-date-field>` — er HTML-tagger, og TypeScript kjenner dem ikke uten videre. Importer typene én gang i en `.d.ts`-fil:

```ts
// src/fristil.d.ts
import "@fristil/designsystem/react-jsx"
```

Da får attributtene autofullføring og sjekk, også de med bindestrek:

```tsx
<fs-field required-marker="text" />      // ok
<fs-field required-marker="tekst" />     // feil: "none" | "symbol" | "text"
<fs-date-field labell="Reisedato" />     // feil: ukjent attributt
<fs-date-field helpText="DD-MM-ÅÅÅÅ" />  // feil: attributtet heter help-text
```

Ren HTML, Astro og Datastar trenger ikke dette — der er `<fs-field>` bare en HTML-tagg.

## Det typene ikke fanger

To ting er verdt å vite:

**Attributtene kan spres på feil element.** `<div {...fs.button({ variant: "danger" })} />` kompilerer. Returverdien er bare et objekt med HTML-attributter, og TypeScript har ingen grunn til å nekte.

**Returtypen på `type` er bredere enn verdien du sendte inn.** `fs.input({ type: "date" }).type` er hele unionen av lovlige typer, ikke `"date"`. Det spiller sjelden noen rolle siden du sprer objektet videre.

## Når du kan hoppe over det

`fs` er valgfritt. Skriver du HTML for hånd, i en mal uten TypeScript, eller i et oppsett uten byggesteg, er dette like gyldig:

```html
<button class="fs-button" data-variant="secondary">Lagre utkast</button>
```

Resultatet er identisk. Forskjellen er bare hvor tidlig du får vite at du skrev `secundary`.

Vil du bare ha én komponent, finnes de som egne inngangspunkter også:

```ts
import { button } from "@fristil/designsystem/button"
```

Subpath-ene returnerer `class` og `for`, som hovedinngangen. React-varianten finnes bare som samlet `fs`.
