Hvorfor vi ikke velger én metodikk

Å låse hele organisasjonen til én teknisk strategi skaper enten vedlikeholdsbyrde eller rigiditet. Ingen enkeltstrategi dekker hele behovet:

Strategi Fordel Kritisk svakhet
Kun ren CSS Zero runtime, full frihet Massiv boilerplate for sammensatte komponenter; ingen sentral A11y-kontroll
Kun React God DX i React-prosjekter Låser org til ett rammeverk – usikker levetid på tvers av app-porteføljen
Kun Shadow DOM Total visuell isolasjon Unødvendig tungt for enkle elementer; blokkerer valideringsmotorer
Løsningen: kategoriser etter faktisk kompleksitet – ikke én størrelse for alt.

Problemet med å kun levere flate CSS-klasser

For enkle elementer fungerer ren CSS utmerket. Men for sammensatte komponenter skyves en enorm vedlikeholdsbyrde over på hvert enkelt team:

  • Massiv copy-paste-boilerplate: Utviklere kopierer 40–50 linjer rå HTML for sammensatte komponenter, og sprer inkonsistens over tid.
  • Ingen sentral A11y-kontroll: Endres HTML-strukturen for å ivareta universell utforming, må samtlige team refaktorere manuelt i egne apper.
  • Visuelle avvik akkumuleres: Menneskelige feil gjør at klasser og attributter utelates, og avvikene øker stille på tvers av team.

De tre arkitektoniske kategoriene

Systemet deles inn etter komponentenes faktiske kompleksitet og funksjonelle behov – frihet under ansvar:

Kategori Teknologi Utviklerfrihet i praksis
A: Global CSS CSS-klasser + data-attributter på native HTML Maksimal. Zero JavaScript-runtime. Alle native HTML-attributter tilgjengelig uten restriksjoner.
B: Light DOM-skall Web Components i Light DOM Svært høy. Skallet håndterer A11y automatisk. Reelle input-felt forblir synlige i DOM – valideringsmotorer har uforstyrret tilgang.
C: Shadow DOM Web Components med Shadow DOM (Lit) Kontrollert. Total visuell isolasjon. Attribute forwarding sikrer at innkapsling ikke skaper friksjon for produktteamene.

Implementering: Kategori A & B

Kategori A (Ren CSS-knapp)

For basiselementer uten ekstra ytelseskostnad.

<button class="ds-button" data-variant="primary" disabled>
  Send inn
</button>
Kategori B (Light DOM-skall)

Tredjepartsverktøy for validering beholder full kontroll over input-feltene.

<ds-field-group>
  <label for="email">E-post</label>
  <input class="ds-input" type="email" id="email" required />
</ds-field-group>

Kategori C: Datovelgeren som eksempel

For komplekse komponenter som en datovelger er Shadow DOM ikke et valg – det er en nødvendighet. Men innkapsling må ikke bli en flaskehals:

  • Style-isolasjon: Shadow DOM hindrer at globale CSS-regler fra vertsappen forskyver dager i kalenderen eller bryter popover-vinduet.
  • Native API-er (2026): Temporal API håndterer all datomatematikk og Popover API styrer overlays – uten tunge JavaScript-avhengigheter.
  • Attribute forwarding: Komponenten fanger opp alle attributter satt eksternt – tracking-ID-er, egendefinerte ARIA-tagger, data-hooks – og spreader dem ned til de interne kjerne-elementene i Shadow DOM.

Teknisk løsning: Attribute Forwarding

Ved å mappe this.attributes dynamisk i Lit, flytter vi utviklerfriheten inn i Shadow DOM uten å miste kontroll:

import { LitElement, html } from 'lit';
import { customElement } from 'lit/decorators.js';

@customElement('ds-datepicker')
export class DsDatepicker extends LitElement {
  render() {
    const forwardedAttrs = Array.from(this.attributes).reduce((acc, attr) => {
      acc[attr.name] = attr.value;
      return acc;
    }, {} as Record<string, string>);

    return html`
      <input type="text" popovertarget="cal" ...=\${forwardedAttrs} />
      <div id="cal" popover><!-- Kalenderlogikk --></div>
    `;
  }
}

Konklusjon & Organisasjonsgevinst

Designsystemet som tilrettelegger – ikke en flaskehals:

Produktteamene beholder fullt eierskap over applikasjonslogikk og skjemavalidering via Kategori A og B. Kategori C avlaster dem for tungt vedlikehold på komplekse komponenter – uten å miste fleksibilitet.

  • 100 % rammeverksuavhengig: Overlever teknologiskifter i app-porteføljen de neste 10 årene.
  • Native ytelse: Nettleseren gjør tungarbeidet (C++) i stedet for klient-JavaScript.
  • Smidig hverdag: Ingen team trenger å refaktorere for å få A11y-oppdateringer fra designsystemet.
