En kodeagent som ikke kjenner LO-TEK gjetter, og den gjetter på de samme fire
tingene hver gang: den glemmer stilarket og skriver egen CSS for å «fikse» at
knappen ser ustilt ut, den finner opp `lt-modal` og `data-variant="outline"`
fordi de finnes i andre designsystemer, den hardkoder `#0062ba` i stedet for å
bruke et token, og den skriver `invalid="false"` og tror det slår av.

LO-TEK har derfor en regelbok skrevet for agenter, med nøyaktig de fire
tingene øverst.

## Regelboka er i pakken

```bash
npx @lo-tek/interfaces agent
```

Kommandoen skriver regelboka for *dette* prosjektet til utdata. Den leser
miljøet av `package.json`, og forteller på feilkanalen hva den valgte og hvorfor,
så utdata kan pipes rent:

```bash
npx @lo-tek/interfaces agent > lotek.md            # til en fil du eier
npx @lo-tek/interfaces agent --rammeverk=datastar    # velg selv
```

Seks regelbøker, én per miljø:

| Navn | For |
| --- | --- |
| `html` | ren HTML uten byggesteg |
| `maler` | Go, Razor, PHP, Blade, Twig, Jinja, Django, ERB, Liquid, Handlebars, Nunjucks, Edge, og HTML bygget som strenger i Kotlin, Java, C# eller Python |
| `bundles` | Vue, Svelte, Solid, Lit, og vanlig TypeScript med Vite, Rollup, esbuild eller webpack |
| `react` | React |
| `astro` | Astro |
| `datastar` | HTML med Datastar |

Vue, Svelte, Solid og Lit deler `bundles`, fordi de gjør det samme med
stilarkene, attributtnavnene og registreringen. `--rammeverk=svelte` virker
likevel, og kommandoen sier at svaret ble `bundles`.

Er pakken installert, ligger den samme fila på disk:

```
node_modules/@lo-tek/interfaces/agent/datastar.md
```

Fila følger pakkeversjonen. Oppgraderer du LO-TEK, er regelboka oppdatert i
samme slengen, og den kan aldri stå og si noe annet enn koden ved siden av.

## Uten å installere noe

Den viktigste agenten har ingen `node_modules`. Blir noen bedt om å «lage et
skjema med LO-TEK» i en tom mappe, skrives markupen før `npm install` har
kjørt, og fila i pakken er da usynlig. Derfor ligger de samme filene her, på
stabile adresser:

| Adresse | Hva |
| --- | --- |
| [`/llms.txt`](https://lo-tek.sobernetics.no/llms.txt) | Inngangen: de fire reglene, sjekkekommandoen, og lenker til alt annet |
| [`/agent/react.md`](https://lo-tek.sobernetics.no/agent/react.md) | Regelboka, komplett. Bytt `react` for miljøet ditt |
| [`/components/button.md`](https://lo-tek.sobernetics.no/components/button.md) | Hver side i dokumentasjonen som Markdown. Bytt `/` på slutten av adressen med `.md` |

Filene er byte for byte de samme som pakken sender med. De bygges av `agent/`
i pakken, og en vaktpost feller hvis de skiller seg. En agent med nettilgang
trenger altså ikke installere noe for å kunne reglene, og `npx` virker også uten
at pakken står i prosjektet.

:::note[LO-TEK skriver ingenting i filene dine]
`AGENTS.md`, `CLAUDE.md` og `.github/copilot-instructions.md` er dine. Et
verktøy som skriver i dem må gjette hvor de ligger, flette teksten sin inn
mellom linjer det ikke har skrevet, og holde kopien i takt med pakken. Ingen
av de tre problemene oppstår når regelboka blir stående i pakken, og
`lotek agent` skriver aldri til en fil. Vil du likevel ha regelboka i en
fil, lagrer du den selv med `npx @lo-tek/interfaces agent > lotek.md`.
Da er det du som bestemmer hvor den ligger.
:::

## Linja du limer inn

Agenten finner ikke regelboka av seg selv. Én linje i instruksjonsfila du
allerede har er nok. Bytt `react` for miljøet ditt:

```md
Prosjektet bruker LO-TEK (@lo-tek/interfaces). Les reglene før du skriver
markup eller CSS: node_modules/@lo-tek/interfaces/agent/react.md, eller
https://lo-tek.sobernetics.no/agent/react.md hvis pakken ikke er installert. Kjør
`npx @lo-tek/interfaces sjekk <fil>` på markup du har skrevet, og
`npx @lo-tek/interfaces sjekk <adresse>` på hver side du har endret, med
appen i gang. Du er ferdig når begge svarer «Markupen stemmer med LO-TEK».
```

Hvor den hører hjemme:

| Agent | Fil |
| --- | --- |
| Claude Code | `CLAUDE.md`, eller `AGENTS.md` |
| GitHub Copilot | `.github/copilot-instructions.md` |
| Cursor, Windsurf og andre | `AGENTS.md` |

Limer du ikke inn noe, er ikke alt tapt: `npx @lo-tek/interfaces sjekk`
forteller agenten hva som er galt i markupen den skrev, med fil, linje og
kolonne. Det er den samme sjekken som editoren kjører, og den kjenner hver
klasse, hvert element, hvert attributt og hver lovlige verdi.

## Hva som står i den

Regelboka er komplett for ett miljø, og bare for det ene. En agent som leser
om `className` i et prosjekt med Go-maler er en agent som skriver `className` i
en Go-mal. Hver av dem har de fire reglene øverst, og så:

- **stilarket**, slik det kommer inn i nettopp dette miljøet;
- **alle komponentene**, med klasse eller element, stilark, attributter og
  lovlige verdier, så ingenting må gjettes;
- **tokenene**, som familie ganger rolle, med navnene skrevet ut;
- **de tre reglene for web components**, som ingen kompilator fanger;
- **sjekken**, med kommandoen og hvordan den kjøres i CI eller i testene.

Filene genereres av pakken. Komponentlista, attributtverdiene, tokennavnene og
byggefunksjonene leses av koden, og en vaktpost i `bun run check` feller hvis en
komponent mangler i en av dem, hvis et markupeksempel ikke tåler LO-TEKs egen
sjekk, eller hvis en importsti ikke finnes i `exports`. En regelbok kan derfor
ikke stå og si noe annet enn koden.

## Sjekken er løkka

En agent retter seg selv når noe forteller den hva som er galt. Det er derfor
regelboka slutter med sjekken, og derfor linja over ber om at den kjøres:

```bash
npx @lo-tek/interfaces sjekk templates/*.html
```

Ett funn gir feilkode, så den hører i CI. Den er laget for maler og lar
malsyntaks være: `{{ }}`, `{% %}`, `<?= ?>`, `@variabel` og `<%= %>` gir
ingen falske funn.

En mal kan ikke vise om koblingen stemmer, for ledeteksten og feltet kan stå i
hver sin fil. Det er nettopp koblingen en agent oftest bommer på. Derfor er
det andre halvdelen av løkka å sjekke siden slik serveren sender den:

```bash
npx @lo-tek/interfaces sjekk http://localhost:8080/form
```

Da krever sjekken også at hver `for` og `aria-describedby` peker på en id som
finnes, og at hvert felt har en ledetekst. Det virker likt i alle språk, siden
det er HTML-en som sjekkes. Flagg og eksempler for tester står på
[Kommandolinjen](../command-line/).

I et typet prosjekt er typene den første sjekken: `lt.button({ variant })`
gjør en variant som ikke finnes til en kompileringsfeil, og importerer du
`@lo-tek/interfaces/react-jsx`, gjelder det samme for attributtene på
web-komponentene. En håndskrevet `className` eller `data-variant` ser ingen
av dem, og heller ikke `lotek sjekk`, som leser `class`, ikke `className`,
så bruk byggefunksjonene. Se [Typesikker bruk](../type-safe-use/).
