Et skjemafelt er tilgjengelig når hjelpeteksten og feilmeldingen er koblet til selve feltet. Fristil gir deg den koblingen på to måter, og **du skal bruke den ene, ikke begge**.

| Lager du markupen med JavaScript? | Bruk |
| --- | --- |
| **Ja.** React, Astro, en Node-server, eller en app helt uten server | [`fs.field()`](#som-funksjon). Da trenger du ikke web componenten |
| **Nei.** En Go-mal, en PHP-fil, en Razor-visning eller håndskrevet HTML | [`<fs-field>`](#som-element) |

Begge bruker den samme funksjonen under, så kontrakten kan ikke gå fra hverandre. Forskjellen er bare om koden som lager HTML-en kan kalle en TypeScript-funksjon.

`<fs-field>` lager ingen markup selv og bruker ikke Shadow DOM, så `FormData`, skjemabiblioteker og testverktøy finner elementene som før.

:::note[Andre komponenter er ikke enten eller]
`<fs-field>` kan erstattes helt av byggefunksjonen, fordi koblingen er markup og ikke oppførsel. Det samme gjelder [Dialog](../dialog/), når appen selv kaller `showModal()`. [Tabs](../tabs/), [Popover](../popover/), [Suggestion](../suggestion/) og [Error Summary](../error-summary/) gjør noe en funksjon ikke kan, som piltaster og fokus, så der bruker du byggefunksjonen **og** komponenten. Se [Markup og oppførsel](/markup-og-oppforsel/#byggefunksjon-eller-web-component).
:::

## Slik tar du den i bruk

`defineFsField()` registrerer web componenten i nettleseren, og kalles én gang ved oppstart. Flere kall er ufarlige. Stilarket må importeres fordi barna er dine egne elementer med klassene `fs-label`, `fs-input` og så videre, og de klassene må ligge på siden. `field.css` samler dem.

  <TabItem label="React">
    I React kaller du `fs.field()`. Da står koblingen i markupen React selv rendrer, på serveren som i nettleseren, og du trenger ikke registrere noe.

    ```tsx
    // main.tsx, kjøres én gang når appen starter
    import "@fristil/designsystem/tokens.css"
    import "@fristil/designsystem/field.css"
    import "@fristil/designsystem/button.css"
    ```

    ```tsx
    // Kontaktskjema.tsx
    import { fs } from "@fristil/designsystem/react"
    import { useId, useState } from "react"

    export function Kontaktskjema() {
      const [navn, setNavn] = useState("")
      const [berørt, setBerørt] = useState(false)

      const ugyldig = berørt && navn.trim() === ""
      const felt = fs.field({
        id: useId(),
        required: "symbol",
        error: true,
        invalid: ugyldig,
      })

      return (
        <form
          noValidate
          onSubmit={(e) => {
            e.preventDefault()
            setBerørt(true)
          }}
        >
          <label {...felt.label}>Fullt navn</label>
          <input
            {...fs.input({ type: "text" })}
            {...felt.control}
            name="navn"
            required
            value={navn}
            onChange={(e) => setNavn(e.target.value)}
            onBlur={() => setBerørt(true)}
          />
          <p {...fs.errorText()} {...felt.error}>Fyll inn navnet ditt.</p>

          <button {...fs.button()} type="submit">Send</button>
        </form>
      )
    }
    ```

    `required: "symbol"` gir stjernen på ledeteksten. At feltet må fylles ut, sier `required` på selve feltet.

    :::caution[I React kommer id-en fra `useId()`]
    En id som lages av seg selv blir ikke den samme på serveren og i nettleseren, og React melder da avvik ved hydreringen på ledeteksten, feltet og feilmeldingen. Advarselen sier selv at avviket ikke blir rettet opp. `createFieldId()` duger heller ikke i en komponentkropp: den gir en ny id ved hver rendring.
    :::

    :::caution[Web componenten gir hydreringsfeil i React med server-rendring]
    Komponenten skriver `aria-describedby`, id-er og klassen på elementene i det den registreres, altså før React hydrerer. React finner da attributter den ikke rendret, og utviklingsbygget i React 19 melder «A tree hydrated but some attributes of the server rendered HTML didn't match the client properties». Feltet virker, men feilen står i konsollen på hver side med et felt. Bruk `fs.field()`.

    Rendrer appen bare i nettleseren, uten server, virker `<fs-field>` også i React. Ugyldig styres da med `hidden={!ugyldig}` på feilmeldingen, et vanlig HTML-attributt React skriver likt i alle versjoner.
    :::

**`fs.input()` skal bare få `type`.** Tilstanden ligger i `felt.control`, og de to overlapper med vilje ikke. Sendte du `state` til begge, ville `aria-invalid` blitt skrevet ut to ganger i maler som gjengir attributtene bokstavelig, som Astro og ren HTML. `felt.state` finnes fortsatt hvis du vil drive noe annet med den.

### Merkingen

`data-required` på ledeteksten velger hvordan et påkrevd felt merkes, `symbol` eller `text`, og står i markupen, så merket synes også før skriptet har kjørt. `optional` på `<fs-field>` snur det om: merk det valgfrie framfor det påkrevde, når nesten alt i skjemaet må fylles ut. `optional` har ingen plass i oppskriften over, siden den viser ett felt og ikke et skjema.

```html
<fs-field>
  <label class="fs-label" for="epost" data-required="text">E-postadresse</label>
  <input class="fs-input" id="epost" type="email" required />
</fs-field>

<fs-field optional>
  <label for="melding">Melding til saksbehandler</label>
  <textarea class="fs-textarea" id="melding" rows="3"></textarea>
</fs-field>
```

## Hvorfor koblingen er vanskelig

Et felt med hjelpetekst og feilmelding krever fem koblinger som må stemme samtidig:

```html
<label for="epost">E-postadresse</label>
<input id="epost" aria-invalid="true" aria-describedby="epost-hjelp epost-feil" />
<p id="epost-hjelp">Vi sender kvittering hit.</p>
<p id="epost-feil">Skriv en gyldig e-postadresse.</p>
```

Hver `id` må være unik, `aria-describedby` må peke på begge tekstene, og `aria-invalid` må følge valideringen. Fem steder å gjøre feil per felt, ganget med antall felt. Og det synes ikke på skjermen når en av dem mangler.

## Som funksjon

`fs.field()` regner ut attributtene der du rendrer, enten ved bygging i Astro, på hver render i React, eller på serveren. Nettleseren trenger ingen registrert komponent, og koblingen står ferdig i HTML-en før noe skript har kjørt:

```tsx
const felt = fs.field({ id: "epost", required: "symbol", help: true, error: true, invalid })

<label {...felt.label}>E-postadresse</label>
<input {...fs.input({ type: "email" })} {...felt.control} />
<p {...fs.helpText()} {...felt.help}>Vi sender kvittering hit.</p>
<p {...fs.errorText()} {...felt.error}>Skriv en gyldig adresse.</p>
```

Bruker du React, importer fra `@fristil/designsystem/react`, som gir `className` og `htmlFor` i stedet for HTML-navnene.

**`id` er påkrevd.** I React kommer den fra `useId()`. Ellers er feltets eget navn som regel det opplagte valget. Vet du sikkert at markupen rendres én gang, som på en Astro-side, kan du kalle `createFieldId()`, som du får fra både `@fristil/designsystem` og `@fristil/designsystem/react`.

Grunnen er at en id som lages av seg selv er tilfeldig: to kjøringer gir to ulike. Rendres det samme feltet på en server og så i nettleseren, peker `for` og `aria-describedby` på noe annet enn det som står der, og React melder avvik ved hydreringen.

Skriver du JavaScript uten typer, ser du ingen type. Da lager funksjonen en id likevel, og sier fra i konsollen, så feltet virker mens du retter det.

## Som element

Kan ikke koden som lager HTML-en kalle en TypeScript-funksjon, gjør `<fs-field>` den samme koblingen i nettleseren. Du skriver elementene dine som vanlig, med `for` på ledeteksten og `id` på feltet, eller med ledeteksten rundt feltet. Det er det HTML krever for at feltet skal ha et navn før skriptet har kjørt, og for at stemmestyring skal finne det. Komponenten setter `aria-describedby` og `aria-invalid` på feltet og gir hjelpeteksten og feilmeldingen id.

Komponenten skriver aldri id på feltet. Datastar og idiomorph kjenner igjen et element på id, og et felt med en id serveren ikke sendte, ville blitt byttet ut ved neste oppdatering, med fokus og det brukeren har skrevet. Uten en id fra komponenten blir feltet stående.

Sender serveren det samme området på nytt mens brukeren holder på, som i en Datastar-app, river morfingen koblingen bort: ingenting av den sto i HTML-en serveren sendte. Komponenten ser det og setter den tilbake, så malen din trenger ingen `data-preserve-attr`. Begrunnelsen står i [Markup og oppførsel](/markup-og-oppforsel/#når-markupen-ikke-lages-med-javascript).

I en løkke lager du id-en av en nøkkel i dataene, som `merknad-{{.Kode}}`, aldri av indeksen eller en teller. En id som følger plassen, flytter det brukeren skrev til feil rad når serveren setter inn en ny. Lager malen id-en av noe som skifter mellom rendringene, sier komponenten fra i konsollen når en oppdatering byttet ut feltet av den grunn.

Finner komponenten ikke delene sine, sier den fra i konsollen. Et `<fs-field>` uten en kontroll gir en advarsel med navnet på det som mangler, framfor et felt som stilltiende står uten kobling. Det samme gjelder et felt uten ledetekst, men bare når det heller ikke har et navn på annet vis: en `<label for>` utenfor elementet, `aria-label` eller `aria-labelledby` på kontrollen teller, som i et søkefelt med bare et ikon. Og et felt med mer enn én kontroll gir en advarsel, siden bare den første får koblingen.

## Automatisk kobling

Hver gang innholdet eller attributtene endrer seg, finner den `<label>` og første kontroll blant sine egne deler og:

1. Setter `label[for]` til kontrollens `id` når kontrollen har en, og ledeteksten ikke står rundt kontrollen. Kontrollen får aldri en id fra komponenten.
2. Gir hjelpetekst og feilmelding `id` ved behov.
3. Setter `aria-describedby` på kontrollen: hjelpeteksten alltid, og feilmeldingen i tillegg når den synes. En skjult feilmelding skal ikke leses opp.
4. Setter `aria-invalid="true"` på kontrollen når feilmeldingen synes, altså har tekst og står uten `hidden` og uten `display: none`. `data-show` i Datastar og `data-text` i en beholder som står tom, virker derfor også.
5. Setter `data-optional` på ledeteksten når `<fs-field>` har `optional`.

Feilmeldingen kan ligge i markupen hele tiden med `hidden`, eller rendres av malen bare når feltet er ugyldig. Komponenten rører aldri `hidden` på den.

Komponenten krever to klassenavn av deg: `fs-help-text` på hjelpeteksten og `fs-error-text` på feilmeldingen. Kontrollen finner den på tagnavnet, altså `<input>`, `<textarea>` eller `<select>`, og et `type="hidden"` teller ikke som kontroll. Ledeteksten finner den på en `<label>` inni elementet, eller på en `<label for>` utenfor som peker på kontrollens `id`. Har kontrollen ingen `id`, og ledeteksten står ikke rundt den, sier komponenten fra: feltet har da ikke noe navn uten JavaScript. Har kontrollen `id` og ledeteksten mangler `for`, skriver komponenten `for` uten å si fra, så skriv den i malen også: uten JavaScript er det den som gir feltet et navn.

Delene er bare dem som hører til dette feltet. Står et `<fs-field>` inni et annet, som et søkefelt i et sprettoppvindu inni feltet, ser det ytre feltet bare sin egen kontroll, ledetekst, hjelpetekst og feilmelding, og det indre sine.

## Attributter

| Attributt | Type | Hva det gjør |
| --- | --- | --- |
| `disabled` | boolsk | Setter `disabled` på kontrollen og demper ledeteksten |
| `optional` | boolsk | Setter `data-optional` på ledeteksten |
| `described-by` | streng | Legger til ekstra `id`-er i `aria-describedby`, i tillegg til hjelp og feil |

Det finnes ikke noe `invalid`-attributt. Feltet er ugyldig når feilmeldingen synes, eller når serveren har skrevet `aria-invalid` på kontrollen. Påkrevd-merket står som `data-required` på ledeteksten, og er bare visuelt: `required` må stå på selve `<input>`.

## Tilgjengelighet

- Komponenten gjør koblingen, ikke innholdet. Ledeteksten og feilmeldingen må du fortsatt skrive godt.
- Skriv `for` på ledeteksten og `id` på feltet, eller legg ledeteksten rundt feltet. Uten det har feltet ikke noe navn før skriptet har kjørt.
- Sett `required` på `<input>` i tillegg til `data-required` på ledeteksten.
- Vis feilmeldingen når brukeren har forlatt feltet, ikke for hvert tastetrykk. Meldingen leses opp hver gang den dukker opp.
- Én kontroll per `<fs-field>`. Komponenten kobler seg til den første den finner. Grupper hører hjemme i en `<fieldset>` med `<legend>`.
