# LO-TEK for IntelliJ

Completion of LO-TEK's CSS classes and diagnostics from LO-TEK's check in HTML,
also in HTML injected into a string.

## Why it exists

`web-types.json` ships with the npm package and gives completion of both the elements and
the classes in the JetBrains IDEs, without anyone installing anything. But it is read
only for **files**, and an injected fragment is not a file.

This has been checked: with `web-types.json` in place, `class="lt-` gives suggestions in an
`.html` file, but nothing in the same markup inside a multiline string.

The plugin closes that gap. It also shows the diagnostics from the check,
which no other source gives in IntelliJ.

## Live templates

Type `lt-field` and press Tab, and the markup from the component page is there, with
the id as a variable and `for` following it. The templates are in
`interfaces/live-templates.xml`, generated by `generate-vocabulary.ts` from the
same recipes as the snippets in VS Code, and Gradle copies the file in as
`liveTemplates/Lotek.xml`. A new component gets a template by itself on the next
`generate`, but the plugin has to be released again for users to get it.

## The diagnostics

`LotekAnnotator` runs the same Rust core as `lotek check` and VS
Code, through the Maven package in `../kotlin`. There the core is compiled to
WebAssembly and then to JVM bytecode, and Chicory runs it in the IDE's own JVM.
No Node, no process to start.

It is an ordinary `Annotator` on the HTML language, for the same reason as the completion:
that way it is also called for injected fragments. The check is `diagnoseMarkup`, because
a file or a fragment is a template. Each finding has the rule name and a link to
the documentation, and a fix when the core has one. A fix can be
several edits, such as `id` on the field and `for` on the label; they are applied from the end,
so the positions hold. In a string each edit is mapped to its part of
the host string and written through the string's own manipulator, so
the quotation marks the fix inserts are escaped in a `"…"` string, and a template
such as `$name` in the string is left untouched. A finding is suppressed with
`<!-- lotek-ignore-next rule-name -->` above the tag.

The check runs against the project's manifest, found the way the language server finds it:
from the folder the file is in and upwards to the project folder, first
`build/lotek/manifest.json`, which the Gradle task `lotekManifest` writes
when the project has taken over components, then
`node_modules/@lo-tek/interfaces/manifest/manifest.json`. For an injected
fragment the search starts from the file the string is in. If neither exists, or the
core cannot read the manifest, the manifest in the Kotlin package applies, and the
latter is written to the IDE's log. See `ProjectManifest.kt`. When the manifest appears, changes or disappears,
the open files are checked again (`ManifestListener.kt`).
Completion reads the classes from the same manifest, see [The data](#the-data).

The annotator runs the core on every file, also one without a single `lt-` class:
the rule `icon-without-name` applies to plain HTML, and `lotek check` and VS Code
report an icon button without a name regardless. A shortcut that skipped files without
"lt-" in the text made IntelliJ stay silent about it.

Gradle builds `../kotlin` with `includeBuild`, and the Kotlin package is built from
the npm package with the same version. Between two releases the one on npm is too old,
so pack it from the repository first, as in `kotlin/README.md`:

```bash
bun --filter @lo-tek/interfaces pack
cd editor-intellij && ./gradlew build -Plotek.package=../interfaces
```

## The string has to be marked

IntelliJ does not inject HTML into a string by itself. It does so when you tell it
to, with `@Language("HTML")` on the function or a `// language=HTML` comment
above the value. Both are built into IntelliJ and need no dependency.

Without such a marker the string is just text to the IDE, and the plugin has
nothing to attach to. So it covers marked strings, not every string
that happens to contain markup.

## How

One registration in `plugin.xml`:

```xml
<completion.contributor language="HTML" order="first" … />
```

Registered on the HTML language, not on Kotlin. When IntelliJ injects HTML into a
string, the fragment becomes a real `PsiFile` with the HTML language, and the contributor
is called for it. The same line therefore covers `.html` files and marked
strings, without one registration per host language.

The tests cover `.html` and Kotlin, for both completion and diagnostics. A marked TypeScript string works for the
same reason, and both have been checked by hand in IntelliJ IDEA Ultimate
2026.2.3.

If you check by hand, the Kotlin file has to be in a module. A loose `.kt` file
in a folder IntelliJ has opened without a module gets no injection, and completion
answers "No suggestions" even with the plugin enabled. `⌥↩` inside the string shows
*Edit HTML Fragment* when the injection is active.

## The data

The classes are read from the manifest the file is checked against: the project's when
`ProjectManifest` finds one, otherwise the manifest in the Kotlin package,
`no/lotek/manifest.json` in the jar. It is the same manifest the core
checks against, so the plugin cannot suggest a class the diagnostics reject, and
it suggests the classes in components the project has taken over. Previously
completion always read the package's manifest, while the check read the project's, and with
an older package installed a class was suggested and then underlined right
afterwards. The manifest is read with `Manifest.parse` in the Kotlin package. See
`Catalogue.kt`.

## Building and testing

Requires JDK 21.

```bash
./gradlew build
```

The first run downloads the IntelliJ platform, around a gigabyte, and takes a
couple of minutes. Later runs take seconds.

The plugin ends up in `build/distributions/` as a zip you can install with
`Settings → Plugins → ⚙ → Install Plugin from Disk`.

## Releasing

The plugin is on [JetBrains Marketplace](https://plugins.jetbrains.com/plugin/34764-lotek)
with the ID `no.lotek`. Three things are worth knowing:

- **The ID can never be changed** after the first upload.
- **The description in `plugin.xml` and `changeNotes` in `build.gradle.kts` are in
  English.** Marketplace requires English as the main language.
- **A new version** gets a new number in `pluginVersion` in `gradle.properties` and
  a line in `changeNotes`. Once it is on master, the tag is pushed
  with `bun run tag intellij`, straight away: the editors page in the documentation
  describes what the latest version does, and is deployed the moment master
  changes, so an untagged version promises something Marketplace does not have. Then
  `publish-intellij.yml` builds, tests and uploads the plugin with the token
  in the secret `JETBRAINS_MARKETPLACE_TOKEN`. The tag must match
  `pluginVersion`. JetBrains approves each version before it becomes visible.
- **The plugin is not signed with its own certificate.** That is optional, Gradle
  skips `signPlugin` without a certificate, and Marketplace signs it itself.

## Why it is not in `bun run check`

The main sequence runs before every push, and already takes a few minutes, see
`CONTRIBUTING.md`. A Gradle build that downloads an IDE does not belong
there. `.github/workflows/ci-intellij.yml` therefore runs on its own, and only when
something the plugin is built from has changed: the plugin itself, the Kotlin package, the core,
the manifest, the package's source code, the rulebooks, the scripts that write them or
`interfaces/package.json`. The paths are in `paths` at the top of the workflow,
with the reason, and it can also be started by hand.
